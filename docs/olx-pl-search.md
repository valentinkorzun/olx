# Поиск по OLX Poland через playwright-cli

Рантайм-инструкция для Claude. Все цифры и имена параметров **проверены на живом сайте 2026-08-21**;
непроверенное помечено явно. Реализация — `docs/snippets/*.js`, справочник категорий — `docs/olx-pl-categories.json`,
локальный кэш — `docs/olx-pl-cities.json` и `docs/olx-pl-searches.json` (см. «Кэш и история»).

## Как это устроено

Данные берутся из внутреннего JSON API `https://www.olx.pl/api/v1/*`, но **из живой браузерной сессии**:
`curl` к тому же URL получает `403` от CloudFront даже с подставленным User-Agent. Браузер здесь — пропуск,
а не способ читать разметку. DOM-скрейпинг оставлен запасным путём (см. «Fallback»).

## Жизненный цикл сессии

```bash
playwright-cli -s=olx open https://www.olx.pl --persistent   # один раз; профиль на диске хранит куки и согласие на cookies
# ... команды ...
playwright-cli -s=olx close                                   # только когда сессия больше не нужна
```

Сессия именованная и переиспользуется между задачами. `--persistent` нужен, чтобы не прогревать куки заново
и не ловить 403 после перезапуска.

## Протокол вызова

Параметры передаются через `window.__P`, снаппет запускается отдельной командой. Файлы сниппетов **не редактируются**.

```bash
playwright-cli -s=olx eval "window.__P={query:'rower',cityId:8959,priceFrom:200,priceTo:500,state:'used'}"
playwright-cli -s=olx --raw run-code --filename=docs/snippets/olx-search.js
```

| Сниппет | Что делает |
|---|---|
| `olx-city.js` | название города → `cityId` (`window.__P.city`) |
| `olx-count.js` | число совпадений по фильтрам, без потолка выдачи |
| `olx-search.js` | поиск → нормализованный массив объявлений |
| `olx-offer.js` | детали одного объявления (`window.__P.id`) |

## Обязательный порядок действий

1. **Перевести запрос на польский.** Поиск работает по польским словам. В ответе пользователю всегда явно
   назвать использованный термин: «ищу по `rower` (велосипед)» — чтобы он мог поправить.
2. **Резолвить город**, если он назван — но сначала `scripts/olx-cache.py city <имя>`. Попадание отдаёт `cityId`
   без сетевого вызова, промах — `exit 3`, и только тогда идём в `olx-city.js`. Резолвер возвращает до 5 кандидатов,
   и **порядок не по релевантности**: на `krakow` настоящий Kraków (`8959`) приходит четвёртым, после деревень
   Krakowiany (с диакритикой, `Kraków`, — первым). Выбирать по точному совпадению имени; при неоднозначности —
   спросить пользователя, а не угадывать. Выбранного кандидата сразу дописать в кэш через `city-add`.
3. **Посчитать совпадения** через `olx-count.js` до самого поиска. Если счётчик — тысячи, не вываливать мусор:
   сказать «слишком широко» и предложить конкретные сужения (цена, город, состояние, категория).
4. **Искать** через `olx-search.js`.
5. **Показать таблицу** топ-N: название, цена (+«торг»), город/район, дата создания, дата поднятия, состояние,
   тип продавца, ссылка. Сырой JSON остаётся промежуточным артефактом. **Ссылку брать только из поля `url`**:
   в адресе `/d/oferta/<слаг>-CID<кат>-ID<base36>.html` сервер разбирает лишь суффикс `ID`, слаг — декоративный.
   Собранный вручную суффикс не даёт `404`, он отдаёт `200` и открывает постороннее объявление
   (проверено 2026-08-21: подделанный id в ссылке на PS5 открыл `majtki-dla-dziewczynki-134-140-CID88`).
6. **Записать запрос** в историю: `scripts/olx-cache.py log --params '<то же, что в window.__P>' --total <счётчик>`.

## Фильтры

Проверено счётчиком `metadata/search` на запросе `rower` (база — 330 777 совпадений):

| `window.__P` | параметр API | проверка | статус |
|---|---|---|---|
| `priceFrom` / `priceTo` | `filter_float_price:from` / `:to` | `from=2000` → 53 587 | ✅ |
| `cityId` | `city_id` | Kraków `8959` → 15 194 | ✅ |
| `distance` | `distance` (км, только с `city_id`) | `8959 + 15` → 18 693 | ✅ |
| `state` | `filter_enum_state[0]` | `used` → 198 875, `new` → 90 388 | ✅ |
| `ownerType` | `owner_type` | `private` → 247 172, `business` → 83 598 | ✅ |
| `courier` | `courier=1` | → 106 162 | ✅ |
| `categoryId` | `category_id` | `1651` → 43 240 | ✅ |
| `sortBy` | `sort_by` | `created_at:desc`, `filter_float_price:asc/desc` | ✅ |

**Имена параметров угадывать нельзя.** API отвечает `200 OK` на неизвестные параметры и молча их игнорирует.
Так провалились правдоподобные `private_business=private` (330 772 против базы 330 777) и `delivery=1` (330 780) —
оба выглядели работающими, пока не сверил счётчик. Любой новый фильтр проверять так же: счётчик до и после.

## Кэш и история

Сессия не помнит прошлый разговор, поэтому одинаковые вопросы («Szczecin? Kraków?») уходили в API снова и снова.
Два файла под контролем версий закрывают это; оба обслуживает `scripts/olx-cache.py` (только stdlib Python 3).

| Файл | Что внутри | Команды |
|---|---|---|
| `docs/olx-pl-cities.json` | `название → cityId` + регион, county, алиасы, дата резолва. Засеян 20 крупными городами (проверены 2026-08-21) | `city <имя>` → JSON или `exit 3`; `city-add --name … --id … [--region … --region-id … --county … --alias …]` |
| `docs/olx-pl-searches.json` | история поисков: дата, `params` (ровно то, что уходит в `window.__P`), `total`, заметка. Новые сверху, хранится 100 | `log --params '<json>' [--total N] [--note …]`; `history [--limit N] [--query …]` |

Поиск по имени нечувствителен к регистру и диакритике: `szczecin`, `Szczecin`, `krakow`, `Kraków` — один ключ.
`history` печатает готовую строку `playwright-cli … eval 'window.__P={…}'` — прошлый запрос повторяется копипастой.

Границы, о которых стоит знать:

- `city-add` ловит только **расхождение** с уже закэшированным id («уже 6169, передан 6681»). Id нового города
  он не проверяет — вписывать исключительно то, что вернул `olx-city.js`, а не «по памяти».
- Кэш не протухает сам. `cityId` у OLX стабильны, но при странной выдаче сверить резолвом и поправить `city-add`.
- История — локальный файл в репозитории, попадает в коммиты. Что не должно там лежать — не логировать.

## Категории

`docs/olx-pl-categories.json` — 19 категорий верхнего уровня и 249 подкатегорий (`id`, `slug`, `name`), собран 2026-08-21.
Публичного справочника у OLX нет: `/api/v1/categories/`, `/categories/tree/`, `/api/v2/` отдают 404, а `/api/partner/categories`
требует OAuth-токен разработчика. Словарь собран из `/sitemap/` (имена и слаги) плюс `category_id` со страницы каждой категории.

Пересобрать при подозрении, что дерево устарело:
- верхний уровень: `GET /api/v1/friendly-links/query-params/{slug}/` → `{data:{category_id}}` (работает **только** для верхнего уровня);
- подкатегории: `GET /{parent}/{child}/` и регулярка `category_id\\*":\s*(\d+)` по HTML (~3.7 МБ на страницу, Range сервер игнорирует).

## Ограничения, которые нельзя обойти

- **Потолок выдачи 1000.** `metadata.total_elements` всегда `1000`, `offset=5000` → `400 Bad Request`.
  При `visible_total_count` в 7862 глубже тысячи объявлений не достать. «Собрать всё» по широкому запросу невозможно —
  только сужать фильтрами. Сниппет ставит флаг `capped: true`, когда упёрся.
- **`limit` максимум 50.** `limit=100` → `400 Data validation error`.
- **Ответ длиннее запрошенного.** `limit=10` → 13 объектов, `limit=40` → 52, `limit=50` → 65: OLX подмешивает промо.
  Поэтому `offset` считается как `i * 50`, а не по числу полученных элементов; дубли режутся по `id`.
- **Промо ломает сортировку.** OLX пришпиливает продвигаемые объявления наверх, и они игнорируют `sort_by`:
  при `filter_float_price:asc` первыми пришли 5249 zł, 3.5 zł, 2999 zł, и только потом органика — строго по возрастанию.
  Фильтры промо при этом **соблюдают** (проверено: 59 карточек, 10 промо, ни одного нарушения по цене, состоянию и городу),
  так что мусора в выдаче нет — сбит только порядок. Каждая карточка помечена флагом `promoted`;
  если нужен строгий порядок по цене, сортировать локально по полю `price`.
- **`seller_type` почти всегда `null`.** У частных продавцов поле пустое; авторитетен булев `business`.
  Сниппеты выводят производный `private` / `business`, а не сырое поле.
- **`created_time` ≠ свежесть.** OLX поднимает старые объявления вверх (`pushup_time`, `last_refresh_time`).
  Сортировка `created_at:desc` смешивает новое и поднятое старое — в таблице показывать обе даты.

## Fallback: DOM

Если API начал отдавать 403 или пустой `data`, разметка выдачи (проверена 2026-08-21):

| элемент | селектор |
|---|---|
| карточка | `[data-cy="l-card"]`, атрибут `id` = id объявления |
| ссылка и заголовок | `[data-testid="card-title-link"]` |
| цена | `[data-testid="ad-price"]` (строкой, `«1 300 zł»`) |
| город и дата | `[data-testid="location-date"]` (`«Gliwice, Sikornik - 06 sierpnia 2026»`) |
| хлебные крошки | `[data-cy="categories-breadcrumbs"]` |

Через DOM цена и дата приходят строками на польском и требуют разбора, а состояния и типа продавца там нет —
это деградация, а не равноценный путь.

## Вне v1

- **Мониторинг новых объявлений** — вынесен сознательно: требует хранения состояния между запусками,
  ключа дедупликации и решения, что считать «новым» при поднятии старых объявлений.
- **Телефон продавца** — `/api/v1/users/me/` отдаёт `401`, контактные эндпоинты требуют авторизации. Не проверялось.
- **Фильтры уровня категории** (марка, размер колеса, материал рамы) — доступны в `/api/v1/offers/metadata/filters/?category_id=N`,
  но в v1 не заведены.
